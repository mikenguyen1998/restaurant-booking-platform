# Booking MVP skeleton handoff

## Reconciliation

The first skeleton had registered 501 routes but no actor-aware booking service, persistence boundary or typed response; owner/admin handlers discarded params/body; FE booking controls were disabled and the restaurantId query was lost. This follow-up supplies those boundaries without implementing booking policy or database writes. No schema/migration changes are included.

Accepted policy remains [#4 reconciliation](../domain/booking-lifecycle.md). Transport types, contact outcome vocabulary and repository method shapes below are **technical proposals**, not new business rules. Secure guest replay/scoping (#12), 24-hour correction reference time, early-COMPLETED release and hold/contact persistence decisions remain pending. Legacy status values in the transport enum support existing schema/history; their presence does not permit creating PENDING/EXPIRED bookings in v1.

## Identity and DI

`BookingsController.create` uses the installed authentication library's `@Authenticate({ optional: true })`, not `@Public()` (which skips identity resolution). `@CurrentUser()` receives the existing session provider's freshly loaded user, or null for a guest. All other booking routes require a session. Service signatures accept server-side `BookingActor` (id/role/emailVerified) separately from transport data; create additionally receives the idempotency key. No request actorId/ownerId/customerId becomes authorization authority. Booking DTO validation rejects unknown properties, including nested identity fields.

`BookingsModule` binds the abstract `BookingRepository` to `PendingBookingRepository`. `BookingsService` is injected with that port but deliberately never invokes persistence while pending. Both layers reject with 501. Tests verify DI, identity forwarding and no fake successful writes; they do not prove ownership/role enforcement. An authenticated customer still reaches 501 on owner/admin scaffolds: services must implement authorization before persistence is enabled.

## Contract and frontend

Shared types: `packages/shared/src/contracts/booking.ts`. `BookingView` is private, while `BookingReceipt` is a deliberately limited proposed create response. The receipt is not a completed secure guest replay design. No guest detail/cancel/reschedule token scheme is invented. Customer history/detail and changes require a session; guest self-service access needs the #12 design first.

All successful response shapes above are **future contracts**, not current 2xx endpoints. Valid requests reach 501. Malformed DTO/UUID/missing create key returns 400; missing protected session returns 401. Existing CORS/CSRF and throttling may reject before reaching the scaffold. No service performs verified-email, time/deadline, availability, ownership, idempotency conflict/replay or lifecycle decisions yet. Requiring a nonempty Idempotency-Key on create/manual-create is a transport proposal; key length/retention/scoping remain technical design, not implemented replay behavior.

FE `src/lib/booking-api.ts` exposes all 19 methods with typed requests/responses, credentials and encoded path/query data. Create forwards restaurantId/date/slot/partySize from discovery. Its per-form intent key stays stable for retries of unchanged input and changes with the input/account; it is not persisted secure guest replay. Customer, owner and admin booking pages provide list/detail/change forms matching the table. Responses/errors come from the API; 501 displays that nothing was saved. No client-side identity is sent as authority. Browser-local hold time is converted to an ISO timestamp; server must validate it against restaurant/booking policy.

The UI deliberately does not fabricate VIP quotes. It remains a scaffold: before enabling real VIP confirmation, implement an explicit fee quote/snapshot/acceptance flow against approved policy. Current discovery availability is advisory and cannot reserve inventory.

## Implement in this order

All use-case methods are in `apps/api/src/modules/bookings/services/bookings.service.ts`; repository signatures are in `repositories/booking.repository.ts`, relative to that module.

1. **Read/access boundaries:** `listMine`, `findOne`, `listOwner`, `findOwner`, `listAdmin`, `findAdmin`. Implement role/customer ownership and restaurant ownership checks, bounded pagination/date ranges, private response mapping and privacy-safe errors. Implement the matching repository read methods. A restaurant ID scopes a target, never proves permission.
2. **Create customer/guest:** `create` and repository `createAtomic`. Resolve verified account vs guest contacts, restaurant timezone and accepted snapshots, cutoff/lead/horizon/closure rules, preference/ranking and VIP fee display/acceptance. Design authorized idempotency scope/fingerprint and guest-safe replay before enabling guest writes. Implement allocation transaction, collision handling, stable ID/reference and durable single confirmation intent together. Existing schema does not yet represent all accepted policy; report/design those gaps separately before changing it.
3. **Customer changes:** `cancel` / `reschedule`; repository `cancelAtomic` / `rescheduleAtomic`. Enforce inclusive snapshot deadline, ownership, atomic release/reallocation and rollback on failure. Retain ID/reference; implement rate limiting and notification intent without duplicate confirmation. Do not choose unresolved policy here.
4. **Owner manual and requested changes:** `createManual`, `cancelOwner`, `rescheduleOwner`; corresponding `*Atomic` methods. Enforce restaurant ownership, reason/contact evidence/audit and the distinction between explicit guest requests, manual bookings and forbidden owner-initiated cancellation of authenticated confirmed bookings.
5. **Owner visit lifecycle:** `recordArrival`, `recordContact`, `extendHold`, `markNoShow`, `correctOutcome`; corresponding `*Atomic` methods. Design persisted arrival/attempt/effective-hold data first; use approved contact/hold/release policy. Keep unresolved correction timestamp/early completion release pending. Review hiding/history and admin escalation need the accepted contract, not a guessed timestamp.
6. **Admin intervention:** `cancelAdmin`, `rescheduleAdmin` with matching atomic repository writes; enforce admin authority, reason/audit and customer notification independently of customer deadline. No admin correction endpoint has been added because its detailed contract is still pending.
7. **Complete end-to-end verification:** replace the pending repository DI binding with a real transactional adapter only after the relevant methods are implemented/tested. Exercise browser auth → discovery → fee acceptance where applicable → confirmed booking → history → cancel/reschedule against real PostgreSQL/Redis. Add notification scheduling/arrival-completion processing only after their technical contracts are settled. The existing cache invalidation race and public review visibility gap remain separate documented application bugs.
